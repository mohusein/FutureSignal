How AI is changing the work of software engineering

Coding assistants now help draft, explain, transform, and test code. Their value depends on the task, the developer, the surrounding workflow, and the quality checks that catch mistakes.

FutureSignal research desk · Publication date pending · Research reviewed October 2026

AI coding assistants are language-model-based tools that generate or edit code from prompts, surrounding files, or a developer’s partial work. They can also explain unfamiliar code, suggest tests, summarize errors, and help navigate documentation. This makes them useful collaborators for some steps in engineering—but the code they produce still needs to be understood and checked.

Where the tools fit

Software engineering includes much more than typing code: understanding requirements, exploring an existing codebase, choosing a design, implementing it, testing, reviewing, deploying, and maintaining it. An assistant can participate in these stages by proposing a next step. It does not automatically know the system’s hidden assumptions, users’ needs, or operational constraints.

For a small, well-specified function, a generated implementation may be easy to evaluate. A change that crosses authentication, data handling, and deployment boundaries requires a broader review. Useful practices include asking the tool to explain its assumptions, limiting the size of a change, and validating the result with tests and independent review.

What the evidence shows

Controlled studies do not support one universal productivity number. In a 2023 experiment with developers completing a bounded JavaScript task, participants given GitHub Copilot finished faster on average; the task and participant pool were specific to that experiment.[1] A later METR randomized trial examined 16 experienced open-source developers working on familiar, mature repositories across 246 tasks. In that setting, developers using early-2025 AI tools took longer on average, despite expecting the tools to help.[2]

These findings can coexist. A short, self-contained task differs from editing a large codebase the developer already knows well. Tool versions, task selection, familiarity, review overhead, and measurement methods all affect outcomes. Neither study establishes how every team or developer will fare.

GitHub also reported a randomized code-quality study involving 202 experienced developers and a short coding task. The company found better scores on several rubric dimensions for code written with Copilot in that experiment.[3] Because the study was run by the tool’s maker and used a bounded task, it is useful evidence about that setup—not independent proof of broad production outcomes.

Workflow and quality

Common uses include generating boilerplate, drafting test cases, translating between languages, explaining unfamiliar APIs, and creating a first version of documentation. They can lower the cost of trying an approach, particularly when a developer can quickly judge whether the result fits.

The same speed can shift work into reviewing, debugging, and integration. A plausible answer may use a deprecated API, miss an edge case, mishandle a permission boundary, or pass a narrow test while violating a product requirement. Measure outcomes that matter to the team—such as accepted changes, defect rates, time through review, and maintenance burden—rather than counting lines generated.

Security and reliability

Generated code should be treated like code from any other source: inspect it, test it, and apply the project’s secure development practices. Review data access, authorization checks, input validation, error handling, dependencies, and secrets. Do not paste confidential code or customer data into a tool unless the organization has approved that use and its data handling.

NIST’s Secure Software Development Framework emphasizes integrating security into the development lifecycle; its companion profile addresses generative AI and dual-use foundation-model development.[4] For application teams, that means keeping threat modeling, code review, dependency checks, and release controls in place even when an assistant suggests the code.

Human judgment and engineering skills

AI changes which tasks are easy to start, but it does not remove the need to reason about correctness. Developers still need to clarify requirements, understand systems, recognize failure modes, and explain why a change is safe. The ability to review code becomes more valuable when more code can be produced quickly.

For learning, ask for explanations and alternatives before delegating the full implementation. Recreate key pieces without assistance, then compare. This keeps the developer engaged in the reasoning needed to maintain the software later.

A practical use model

  1. Give the assistant a bounded task and relevant, non-sensitive context.
  2. Ask it to state assumptions and identify likely edge cases.
  3. Review the proposed diff before running it.
  4. Run tests, linters, and security checks appropriate to the project.
  5. Keep only changes the maintainer can explain and support.

The useful question is not whether AI “replaces” engineers. It is which parts of a particular workflow it improves, what review costs it adds, and how the team will know whether the change made the software better.
